System Architecture v1.0

Feel Good

Complete system architecture and phased development plan for an AI-powered personal mentor that understands a person's life, defines meaningful goals, and guides them toward those goals through personalized, actionable steps.

System Overview

Feel Good is not a collection of tracking tools with an AI chatbot attached. It is a mentor-first architecture where a single orchestration layer drives every user interaction. The habit, wellness, and finance modules exist as tools the mentor calls — not as standalone products with their own navigation and workflows.

The architecture enforces a separation of concerns between three responsibilities: the LLM reasons about the user's situation and proposes actions; application services validate those proposals against real data and business rules; and the user approves consequential changes before they are persisted.

Design Principles

LLM proposes, code validates

The model generates reasoning and personalized guidance. Application services own facts, calculations, and enforcement. The model never writes directly to the database.

Structured over semantic

Goals, deadlines, preferences, and progress are stored as typed fields in PostgreSQL. Vector search is reserved for unstructured content like journal entries and reflections.

User approval for consequences

Any action that creates, modifies, or deletes a goal, plan, or commitment requires explicit user confirmation. The mentor explains; the user decides.

One orchestrator, many tools

A single mentor orchestrator manages all interactions. Domain-specific logic lives in services exposed as narrowly-scoped tools, not in autonomous agents.

Model-agnostic integration

LLM interactions go through an internal interface. The application logic does not depend on a specific model provider, so switching from Azure OpenAI to another provider requires only adapter changes.

Progressive data collection

The system never requires information upfront. It asks questions when answers would materially change a plan, and stores responses as structured fields for reliable downstream use.

Service Architecture

Services are Django apps within a single deployable unit. They communicate through Python function calls, not HTTP — there is no microservice overhead. Each service owns its models, serializers, and business logic. The mentor orchestrator coordinates between them.

Mentor Orchestration Service

Core

The orchestrator is the central intelligence layer. Every user message — whether it's a question, a check-in, or a goal creation request — flows through this service. It determines what the user wants, assembles relevant context, invokes the LLM with appropriate tools, validates the response, and routes approved actions to the correct service.

Internal components

ComponentResponsibility
IntentClassifierCategorizes the user's message: create_goal, check_in, ask_question, revise_plan, log_progress, general_chat. A lightweight classification (could be rule-based or a smaller model) that determines which tools and context to prepare.
ContextBuilderAssembles a context window for the LLM. Pulls the user's active goals, recent progress, relevant profile fields, conversation summary, and any retrieved memories. Applies a token budget to keep the context within limits.
ToolRegistryManages available LLM tools and their permission levels. Filters tools based on intent (a simple question doesn't need write tools). Validates tool call arguments before execution.
ResponseValidatorValidates LLM-generated structured output against JSON schemas. Checks date consistency, budget feasibility, and required field completeness for goal proposals.
ApprovalManagerHolds proposed changes in a pending state until the user confirms. Manages the proposal lifecycle: draft → presented → approved/rejected/edited.
ActionExecutorRoutes validated, approved actions to the correct service method. Wraps each action in a database transaction. Logs the action for audit.

Not every request needs every step. A simple question (“When is my savings goal deadline?”) goes through intent classification, a single tool call to get_goal_detail, and a direct response. The full pipeline activates only for complex planning requests.

Goal Planning Service

Core

Owns the complete goal hierarchy: life directions, long-term goals, milestones, short-term goals, daily actions, and linked habits. This service handles the structural logic that the LLM should not be responsible for.

Goal hierarchy

Life Direction — “The person I want to become”
└── Long-term Goal — measurable outcome, months to years
└── Milestone — intermediate achievement with deadline
│ └── Action — one-time task
│ └── Action — one-time task
└── Milestone
└── Action
└── Linked Habit — recurring behavior supporting the goal

Service responsibilities

  • Hierarchy management: Create, update, reorder, and archive goals at every level. Cascade status changes (completing all milestones marks the goal complete).
  • Time budget validation: Verify that proposed weekly_time_budget_hours across all active goals does not exceed the user's declared available time.
  • Conflict detection: Flag scheduling conflicts when milestones from different goals have overlapping deadlines and insufficient time budget.
  • Progress aggregation: Roll up action/milestone completion into goal-level progress percentages. Distinguish outcome-based progress (measurable criteria) from behavior-based progress (habit consistency).
  • Stall detection: Identify goals where no progress has been logged for a configurable threshold (default: 14 days). Feed these into the mentor's context during check-ins.
  • Plan history: Record every plan revision with a reason field, preserving the original plan and all subsequent changes.

User Profile Service

Manages the structured representation of the user that the mentor relies on for personalization. Profile data is collected progressively through onboarding conversations and updated as the user's circumstances change.

Profile domains

DomainStored fieldsCollection
PersonalAge range, timezone, schedule type, weekly available hours, communication preferencesOnboarding
CareerCurrent role, skills, career ambitions, learning goals, study hours/weekWhen career goals are set
HealthFitness level, activity frequency, equipment access, dietary preferences, optional measurementsWhen wellness goals are set
FinancialIncome range, budget categories, savings targets, financial prioritiesWhen finance goals are set
LifestyleSleep schedule, hobbies, social commitments, travel patternsProgressively

The profile is stored as a combination of typed database fields (timezone, available hours, income range) and a JSONB column for less structured preferences. The typed fields drive application logic; the JSONB data provides additional LLM context.

Conversation Service

Handles message persistence, conversation threading, context window assembly for the LLM, and conversation summarization.

  • Message storage: Every user message, assistant response, and tool call is persisted with timestamps and metadata. Tool call results are stored alongside the message that triggered them.
  • Context window management: Maintains a rolling window of recent messages. When the window exceeds a token threshold, older messages are summarized and the summary replaces them in the active context.
  • Conversation purposes: Each conversation has a purpose (onboarding, check_in, planning, general) that determines the system prompt and available tools.
  • Streaming delivery: Uses WebSocket connections to stream LLM responses token-by-token to the frontend, providing a responsive conversational experience.

Memory Service

Three tiers of memory, each optimized for a different retrieval pattern.

TierStorageUse caseRetrieval
Structured facts PostgreSQL typed fields Goals, deadlines, preferences, approved plans, progress records, commitments Direct query by user ID and field. Exact, authoritative answers.
Conversation summaries PostgreSQL text + metadata Compressed history of past discussions, decisions made, questions asked Recent summaries loaded by timestamp. Prevents the mentor from repeating itself.
Semantic memory pgvector embeddings Journal entries, reflections, detailed context from past conversations Cosine similarity search when the mentor needs nuanced context about the user's experiences.

Never answer factual questions from conversation summaries. If a user asks “How many workouts did I complete this month?”, the system queries the actual workout log records and calculates the result. Summaries are context, not a source of truth.

User control

Users can view everything the system remembers about them, correct inaccuracies, delete specific memories, and opt out of semantic memory collection entirely. Memory consent is granular by category.

Domain Services

Three domain modules, each built as a Django app with its own models, serializers, views, and LLM tools. They share a common pattern: the user or mentor logs data, the service calculates analytics, and those analytics feed back into the mentor's context.

ServiceModelsKey metricsLLM tools exposed
Habits Habit, HabitLog Completion rate, current streak, longest streak, consistency score get_habit_summary, log_habit, create_habit
Finance ExpenseCategory, FinancialRecord, Budget Monthly spend by category, savings rate, budget adherence, spending trend get_expense_summary, log_expense, get_budget_status
Wellness WellnessRecord (polymorphic: workout, measurement, nutrition, sleep) Training frequency, volume trends, measurement changes, sleep consistency get_wellness_summary, log_wellness, get_measurement_trend

Each domain service links its records to goals when relevant. A habit can reference the goal it supports, so progress in the habit feeds into milestone progress tracking.

Data Architecture

All data lives in a single PostgreSQL instance with the pgvector extension enabled. The schema is divided into four groups: core identity, goal hierarchy, domain tracking, and memory.

LLM Integration

The LLM is a reasoning engine, not a database or an action executor. It receives structured context, reasons about the user's situation, and emits structured proposals. Application code handles every side effect.

Tool Framework

Tools are Python functions registered with the mentor orchestrator. Each tool has a typed schema, a permission level, and an ownership check. The LLM sees them as function definitions in the OpenAI function-calling format.

Permission levels

LevelBehaviorExamples
ReadExecutes immediately. Returns data owned by the current user.get_user_goals, get_expense_summary
WriteExecutes immediately for low-consequence writes.log_habit, log_progress
Write + ApprovalCreates a proposal. The user must approve before the change is persisted.create_goal_proposal, propose_weekly_plan

Context Management

The ContextBuilder assembles a structured context object for each LLM call. It applies a token budget to ensure the total prompt stays within model limits.

Context assembly priority

  1. System prompt — Role definition, behavior guidelines, current date and timezone. Always included.
  2. Active goals summary — Compact representation of the user's goal hierarchy with progress. Always included when goals exist.
  3. Profile snapshot — Relevant profile sections based on the detected intent. Career fields for career questions, fitness fields for workout discussions.
  4. Recent conversation — Last N messages from the current conversation. Truncated and summarized when exceeding the token budget.
  5. Conversation summary — Compressed summaries of earlier conversations, prioritized by recency and relevance.
  6. Retrieved memories — Semantic memory results when the intent suggests historical context would help. Only included when the vector search returns results above a similarity threshold.
  7. Domain context — Recent habit completions, expense totals, or wellness data. Included only when the intent relates to a specific domain.

Token budget allocation: 40% for system prompt + goals + profile (static context), 35% for conversation history, 15% for retrieved context, 10% reserved for the model's response. Exact ratios are configurable per model.

Safety and Validation

  • Ownership enforcement: Every tool call passes through a middleware that verifies the requested resource belongs to the authenticated user. The LLM never receives another user's data.
  • Schema validation: All structured LLM output (goal proposals, weekly plans) is validated against JSON schemas before processing. Malformed output triggers a retry with explicit formatting instructions.
  • Date sanity checks: Target dates must be in the future. Milestone dates must fall before the parent goal's target date. Proposed time budgets cannot exceed available hours.
  • Rate limiting: Per-user limits on LLM calls (configurable, starting at 50 messages/day) prevent abuse. Background summarization and memory extraction run on a slower model to manage cost.
  • Content filtering: The system does not provide medical diagnoses, specific investment advice, or therapy. The system prompt clearly scopes the mentor's role, and output is monitored for boundary violations.
  • Audit logging: Every LLM interaction — prompt, response, tool calls, and outcomes — is logged for debugging and evaluation. Logs are retained for a configurable period.

Security model

  • Transport: TLS everywhere. No plaintext HTTP.
  • Authentication: JWT with short-lived access tokens. Refresh token rotation on each use. Tokens stored in httpOnly cookies.
  • Secrets: All credentials in Azure Key Vault, accessed via managed identity. No secrets in environment variables or code.
  • Data encryption: PostgreSQL TDE (transparent data encryption) at rest. Sensitive profile fields encrypted at the application layer with user-specific keys.
  • Row-level isolation: Every query filters by user_id. Django middleware enforces ownership. The LLM tool layer provides an additional ownership check.
  • Rate limiting: Per-user, per-endpoint limits. LLM endpoint has additional daily message caps. Redis-backed token bucket algorithm.
  • CORS: Restricted to the frontend domain only.

Observability

  • Application Insights: Request tracing, dependency tracking, exception monitoring. Custom metrics for LLM latency, tool call success rates, and proposal approval rates.
  • Structured logging: JSON-formatted logs with correlation IDs. Every LLM interaction logs prompt size, response size, model used, latency, and tool calls made.
  • Alerts: Error rate thresholds, LLM latency p95, database connection pool exhaustion, rate limit breaches.
  • Cost monitoring: Azure Cost Management alerts on LLM token consumption. Per-user token usage tracked for capacity planning.
